# 지원자 검증 강화: 회사 개발 인수인계

작성일: 2026-10-12

상태: 사용자 검토를 반영한 개발 요구사항. 이 커밋은 문서만 추가하며 제품 구현, 실제 데이터 분석, 운영 검증 완료를 뜻하지 않는다.

## 1. 목적과 적용 기준

실전용 채용 어시스턴트에서 담당자가 JD 요건과 후보자 근거를 대조하고, AI의 누락·과대해석을 발견해 정정할 수 있게 한다. 채용 판단은 사람이 한다.

- 공개 초기 버전 조사 기준: `e7f46e206c3856389da5b1e4d99c88ff14c0f208`.
- 회사 개발본은 실제 자료와 사내 AI API를 사용하는 방향으로 개발 중이라는 사용자 설명을 전제로 한다. 회사 최신 코드·연동 상태는 이 문서 작성자가 검증하지 않았다.
- 회사 현재 구현과 대조하여 이미 충족된 항목은 유지하고, 미충족 항목만 개발한다. 초기 버전의 Mock 상태를 회사 버전의 상태로 단정하지 않는다.
- 이 문서는 [AGENTS.md](../AGENTS.md), [고위험 검토 기준](rolefit-high-risk-review-harness.md), [회사 연동 경계](rolefit-company-integration.md)를 따른다. 공개 문서와 회사 정책이 다르면 더 보호적인 기준을 적용한다.
- 회사 개발 브랜치·사용자 변경을 유지한다. 이 인수인계 브랜치를 회사 코드에 무조건 병합하거나 초기 코드로 되돌리지 않는다.

## 2. 검증의 세 단계

| 단계 | 확인 결과 | 확정할 수 없는 내용 |
|---|---|---|
| 원문 확인 | 해당 후보자의 특정 자료·버전에 인용이 존재함 | 제출 내용의 외부 진실성 |
| 요건 연결 | 인용의 문맥이 승인된 JD 요건과 관련됨 | 복합 요건 전체 충족, 실제 수행 수준 |
| 사람의 수행 확인 | 면접·과제·산출물 설명에서 담당자가 확인한 사실과 범위 | AI가 자동 확정한 역량·합불 |

인용이 있다는 이유로 역량을 검증 완료로 표시하지 않는다. 동일 모델의 반복 확인이나 Rule/AI 의견 일치를 독립적인 사실 검증으로 표현하지 않는다.

## 3. 초기 코드에서 대조할 항목

아래는 조사한 공개 기준선의 사실이다. 회사 개발본에 남아 있는지 먼저 확인한다.

| 위치 | 초기 동작 | 회사에서 확인할 계약 |
|---|---|---|
| `lib/matching/rubric.ts` | 요건 추출 결과를 최대 8개로 자름 | 모든 요건 처리 또는 미처리 요건 명시. 조용한 누락 금지 |
| `lib/matching/rubric.ts` | 섹션 접두어를 제거한 뒤 필수 여부 분류 | 필수·우대, 섹션 상속과 원문 출처를 먼저 보존 |
| `lib/matching/aiAdapter.ts` | 인용이 후보자 텍스트에 포함되는지 검사 | 유효 요건 ID, 후보자·문서 버전, 문맥·관련성을 별도 검증 |
| `lib/documentExtraction.ts` | 원문 위치 구조 없이 평문 중심 반환 | 보존한 텍스트 구간으로 이동 가능. 페이지 미확보 시 추정 금지 |

| `app/components/ReportView.tsx` | 매칭 퍼센트 및 강한 매칭 표시 | 자료 근거·미확인 사항을 우선하고 점수의 의미·한계 명시 |
| `lib/server/analysisService.ts` | Mock adapter 및 프로세스 메모리 기반 실행 관리 | 사내 adapter, 저장·재시작·권한 경계를 회사 구현과 대조 |

## 4. 우선 구현 요구사항

### V1. 기준 확정과 요건 누락 방지

- JD를 검토 가능한 최소 단위로 분리한다. 필수·우대와 AND/OR 관계, 원문 구간을 보존한다.
- 승인된 요건 집합·버전을 후보자 분석에 고정한다. 새 요건 제안은 별도 초안으로 남기고 승인 전 판정에 사용하지 않는다.
- 조직 전략·목표·주관 의견은 승인된 JD와 연결된 범위에서만 사용한다. 숨은 평가 조건을 만들지 않는다.
- 모든 승인 요건은 처리 결과 또는 미처리 목록에 나타난다. 요건 수 제한이 필요하면 사용자에게 제한과 남은 항목을 알린다.
- 모든 후보자에 동일 기준을 적용한다. 진행 중인 전형에 기준을 조용히 변경하지 않는다.

### V2. 원문 인용과 관련성 검증

- AI 출력은 승인 요건 ID, 문서 ID·버전과 원문 구간을 참조한다. 서버는 실제 입력 범위와 인용 존재를 검사한다.
- 정규화 후 인용 일치를 사용해도 원문과의 위치 대응을 보존한다. 같은 문장이 반복되면 실제 문서 구간을 특정한다.
- 인용이 존재하지만 해당 요건을 뒷받침하지 못하면 관련성 확인 필요로 표시한다.
- 경력 진위·성과 원인·실제 기술 수준은 CV만으로 확정하지 않는다.
- 문서의 명령문은 자료로만 취급한다. 후보자 자료에 있는 판정 지시·점수 조작 문구로 시스템 규칙을 바꾸지 않는다.

### V3. 문맥·범위의 과대해석 방지

- 부정·학습·관심·예정과 실제 수행을 구분한다. 한국어·영어·혼용 사례를 검사한다.
- 본인 수행, 팀 참여, 관찰·보조의 범위를 구분한다. 팀 성과를 개인 성과로 확정하지 않는다.
- 실험실·시뮬레이션·실장비·생산 적용을 구분한다.
- 숫자 성과는 기준선·조건·기간·본인 역할의 확인 여부를 함께 표시한다.
- 문서에서 찾지 못했다는 사실을 역량 부재나 부정행위로 바꾸지 않는다.

### V4. 독립적인 상태 표시

| 축 | 최소 상태 |
|---|---|
| 자료 처리 | 정상 / 일부 누락 가능 / 분석 불가 |
| 근거 관계 | 직접 관련 / 간접 관련 / 정상 처리된 자료에서 찾지 못함 / 판단 보류 |
| 사람 확인 | 미확인 / 확인 / 반박 / 보류 |
| 생성 출처 | 사내 AI / Rule / AI 실패 후 대체 결과 |

파싱 실패를 근거 없음으로 변환하지 않는다. API timeout·형식 오류·허위 인용 실패를 정상 AI 결과로 숨기지 않는다. 대체 결과는 출처와 한계를 명시하며, 대체 처리 자체가 분석 성공을 뜻하지 않는다.

### V5. 확인·정정과 재현성

- 결과 카드의 고정 순서: 요건, 인용·출처, AI 해석, 확인한 범위, 남은 질문, 사람 판단.
- 원문 보기로 바로 이동한다. 이번 주에는 추출 텍스트의 문단·구간 강조를 최소 범위로 구현할 수 있다. PDF 페이지가 없으면 만들지 않는다.
- 담당자 확인·반박·보류와 사유를 기록한다. AI 초안과 사람 확정본을 구분하고 정정 이력을 보존한다.
- 분석 실행에 JD/CV 버전, 입력 식별자, 파서·모델·프롬프트·규칙 버전과 생성 시각을 남긴다.
- 저장 결과를 다시 열 때 자동 재분석하지 않는다. 명시적 재분석은 새 실행으로 기록한다.
- 같은 입력의 반복 실행은 표현 일치보다 요건 상태·인용·확인 질문의 치명적 변경 여부를 점검한다.

### V6. 현업 확인 질문 연결

- 관련 요건·근거·미확인 사항에 질문을 연결한다. 본인 역할, 적용 환경, 검증 방법, 실패 사례와 산출물을 확인한다.
- 공통 핵심 질문·판단 기준은 선발 전에 정하고 동일 적용한다. 후보자별 후속 질문은 제출 내용의 사실 확인에 사용한다.
- 회신됨과 역량 확인됨을 구분하고, 현업이 확인한 근거와 범위를 남긴다.
- 회사 비밀·전 직장의 제한 자료 제출을 요구하지 않는다. 공개 가능한 경험·방법 설명을 우선한다.

## 5. 이번 개발 순서와 제외 범위

1. 회사 최신 코드·자료 처리·AI adapter를 대조하고 기준선 테스트를 실행한다.
2. V1~V4의 계약과 실패 사례를 먼저 고정한다.
3. V5의 원문 확인·정정 UI와 저장을 연결한다.
4. 기존 질문·현업 포털에 V6를 연결한다. 새 대규모 전형 시스템을 만들지 않는다.
5. 회사 승인 환경에서 별도 검증 자료로 현업 검수 후 제한된 운영 범위를 결정한다.

이번 주 필수 범위에서 제외: 자동 순위·합불, 새로운 종합점수, 기존 우수 직원 유사도 기반 선발, 전체 OCR 확대, 화상 면접·녹음 서비스 개발, QoH 예측 모델.

기존 숫자 표시를 유지한다면 계산 출처와 한계를 확인하고 확률·신뢰도·실제 역량이라는 명칭을 쓰지 않는다. 확인된 요건 수를 표시할 때 전체 대상 요건과 미처리 수를 함께 표시한다.

## 6. 수용 기준과 검증 사례

| 사례 | 기대 결과 |
|---|---|
| 긴 JD의 뒤쪽에 필수요건 존재 | 결과 또는 명시적 미처리 목록에 포함 |
| 필수요건 섹션의 여러 항목 | 항목별 필수 속성·논리 관계 보존 |
| 원문에 없는 AI 인용 | 확정 근거로 노출하지 않고 오류 상태 표시 |
| 원문에 있으나 다른 요건의 인용 | 관련성 확인 필요, 잘못된 충족 판정 차단 |
| 학습·예정·영어 부정·팀 참여 | 실제 개인 수행으로 확정하지 않음 |
| 표현이 다른 동등 경험·한영 혼용 | 누락 검수 대상에 포함, 단순 키워드 부재만으로 배제하지 않음 |
| 스캔·손상·부분 추출 실패 | 분석 불가/부분 누락 표시, 낮은 역량으로 변환하지 않음 |
| 다른 후보자·문서 버전 인용 | 대상 불일치 차단 |
| 문서 안에 판정 조작 지시 존재 | 자료로 처리, 시스템 명령으로 실행하지 않음 |
| AI 오류·재시도·재시작 | 출처·실패 표시, 권한 확인, 저장 이력과 재시도 일관성 |
| 정정·다운로드 | 화면과 출력의 초안/확정/정정·출처 상태 일치 |

- 소수 합성 사례만 통과하고 전체 정확도를 보장했다고 보고하지 않는다.
- 현업 전문가가 요건·인용의 기대 답을 먼저 정한 검증 자료를 사용한다. 구현 조정용 사례와 최종 확인용 사례를 구분한다.
- 과대해석과 중요한 근거 누락을 따로 집계한다. 이름·연락처 등 직무와 무관한 정보만 바꾼 합성 입력도 검사한다.
- 같은 검토 범위에서 사람 단독과 도구 보조의 소요 시간·정정·누락을 기록한다. 임의 정확도·시간 절감 수치를 약속하지 않는다.
- 필수요건 누락, 후보자 오연결, 허위 인용, 실패 은닉, 비인가 열람이 발견되면 해당 결과 확정·공유를 중단하고 원문 수동 검토 경로를 제공한다.

코드 변경 후 회사 환경에서 실행할 기본 명령:

```powershell
npm.cmd test
if ($LASTEXITCODE -ne 0) { throw 'Tests failed' }
npm.cmd run typecheck
if ($LASTEXITCODE -ne 0) { throw 'Typecheck failed' }
npm.cmd run build
if ($LASTEXITCODE -ne 0) { throw 'Build failed' }
```

여기서 코드 테스트 성공은 실제 문서의 추출·관련성 정확도나 운영 권한 검증의 대체 증거가 아니다.

## 7. 회사 개발자 시작 요청

> 회사 최신 구현, AGENTS.md와 이 문서를 먼저 대조해 충족/미충족/확인 필요를 정리한다. 실제 데이터 사용·AI 전송·저장 권한을 회사 정책 안에서 확인하고, 현재 검증 강화를 TDD로 순차 구현한다. 이미 구현된 기능을 초기 공개 코드로 되돌리지 않는다. 실제 자료·회사 API 정보·인증정보는 개인 GitHub나 외부 개발 에이전트에 보내지 않는다. 위 수용 기준을 기능별로 확인하고 미검증 사항을 보고한다.

공개 저장소에는 이 일반화된 문서와 합성 검증 계약만 남긴다. 회사 실제 코드·자료·검수 결과는 승인된 내부 저장소에서 관리한다.
